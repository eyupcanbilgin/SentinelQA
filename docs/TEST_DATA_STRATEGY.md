# Test data strategy

WorkforceOps uses only fictional names, `example.test` email addresses and synthetic salaries. Never restore an employer's database or paste personal HR records into fixtures, traces or AI prompts. Demo data is a reproducible application fixture; it is not a shared source of mutable data for every test layer.

The `demo` profile creates employee1, employee2, manager, HR and admin accounts with the development-only password documented in [API_CONTRACT.md](API_CONTRACT.md). Their UUIDs and departments are fixed so relationship checks remain readable. Employee1 reports to the manager; employee2 is outside that manager's reporting scope. Every seeded employee starts with 20 calendar days. An employee created through `POST /api/employees` does not automatically receive a login account.

| Layer | Data boundary | Cleanup / parallelism |
| --- | --- | --- |
| Unit | In-memory value inputs, explicit dates and decimal strings | No database or cross-test state. |
| PostgreSQL integration/API | A migrated PostgreSQL test database; demo identity relationships plus test-owned mutations | `PostgresIT` resets requests, runs/items, audit rows and balances before each test. Tests run sequentially; concurrency checks create their own controlled parallel operations inside one test. A test-method transaction does not roll back HTTP server transactions or async workers. |
| Playwright | Demo database dedicated to the whole browser run; separate authenticated browser contexts for roles | One worker and zero blanket retries. Unique future leave dates and unique payroll periods reduce collision; reset the disposable Compose database before a fresh whole run because finalized approvals consume balance. |
| k6 | Disposable performance environment and synthetic workloads | Never run write-heavy scenarios against the browser/API test database concurrently. Payroll periods and leave entitlements are finite resources, not reusable identifiers. |
| Agent evaluations | Versioned evidence fixtures with stable labels | No production logs, network calls or credentials in deterministic CI. |

Date uniqueness does not restore leave entitlement. Likewise, deleting a browser context does not undo an approval. A full environment reset is an explicit local operation against the disposable database; it is not a test helper that silently destroys a developer's data. Follow the reset command and scope in the repository quick start.

Use a UUID or run identifier in generated employee names/emails and test-owned reasons. Payroll periods must obey `YYYY-MM` and be unique within the database. Prefer known future dates for deterministic duration tests; tests for calendar boundaries should supply those boundaries directly rather than depending on today's date. Decimal expectations must be constructed from strings, not binary floating point.

Stateful scenarios belong in one explicit workflow test: create a leave request, perform role-specific approvals, then compare persisted balance before and after. The API's `availableDays` is spendable entitlement after pending reservations, so it decreases at creation and must not decrease again at final approval. PostgreSQL assertions separately inspect stored entitlement and reserved days to prove final approval consumes exactly once. A rejection scenario must prove the reservation is released and no stored balance was consumed. Approval replay and concurrent reservation checks must compare state as well as HTTP responses. Async payroll tests poll terminal state with a bounded deadline and fail with the observed run state; they must not infer completion from the initial `202`.

The preferred integration database is a fresh Testcontainers PostgreSQL instance. An explicitly configured external PostgreSQL instance is a local fallback when containers cannot run; it must be dedicated to tests and use the same migrations. `PostgresIT` truncates `payroll_items`, `payroll_runs`, `leave_requests` and `audit_events`, restores balances to 20/unreserved, and reactivates employees before each test. External mode therefore destroys mutable state in the selected database; never point it at a developer's persistent Compose database or any shared environment. See [integration instructions](../tests/integration/README.md) for the explicit settings. That fallback is not evidence that Testcontainers executed. Never substitute an in-memory database to make migration or locking tests appear verified.

Failure artifacts may contain demo salary and leave-reason fields. Limit their retention and restrict uploads to the required report/trace files. Sanitize bearer tokens, passwords, authorization headers and sensitive free text before optional provider calls. A correlation ID is an identifier, not a credential; use bounded synthetic IDs without personal information.
